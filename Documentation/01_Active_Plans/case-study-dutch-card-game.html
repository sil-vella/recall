01 — In short

A real card game, not a template demo

Dutch is a digital take on the Dutch shedding / memory card game: clear your hand or finish with the lowest points, call Dutch to lock the endgame, and climb ranks with coins on the line. It ships on the App Store and Google Play under com.reignofplay.dutch. The codebase behind it is an older Reign of Play stack — Flask and MongoDB for durable product truth, a Dart WebSocket server for hot match traffic, Flutter for the client — not the newer FastAPI / Postgres template.

02 — The problem

Ship a game, then keep running it alone

Building Dutch meant more than cards on a screen: accounts and guests, coin stakes, rank progression, practice AI vs real multiplayer, App Store and Play billing, ads, and a VPS that stays healthy through deploys.

After launch, the same solo loop continues — releases, social posts, and revenue checks. A CLI script menu helps, but I still needed a browser desk for marketing, revenue, docs, and planning next to the code that ships the game.

Goal: one product repo that is both the live Dutch game and the ops surface I use every week — honest about its older stack, not rewritten as a template story.

03 — Pillar 1 · The game

Dutch rules players already know, online

Draw, play, peek with Queens, swap with Jacks, call Dutch, win by emptying your hand or lowest score. Modes include live multiplayer lobbies and local practice against CPU. Clear-and-collect adds a set-completion win path.

What players feel

  • Coin-gated multiplayer tables with rank / table tiers
  • Progression from wins → level → rank (declarative catalogs)
  • Shop cosmetics and consumables; premium / promotional tiers
  • Guest or Google sign-in; Apple and Google Play purchases
  • AdMob rewarded paths alongside IAP

Why it matters

  • Shared match rules run on Flutter and the Dart game server — one mental model
  • Practice doesn’t burn coins; multiplayer stakes feel real
  • Store listing: Dutch Card Game · Apple ID 6772967073

04 — Pillar 2 · Live stack

Older base, still the production truth

Dutch did not migrate to the FastAPI / Postgres template. Production authority is python_base_04 Flask with MongoDB and Redis. Hot multiplayer traffic goes through dart_bkend_base_01. The client is flutter_base_05 with manager-based modules (auth, nav, dutch_game, ads, billing).

  • Flask — REST, Socket.IO helpers, module registry / AppManager
  • MongoDB — users, dutch_game module docs, catalogs
  • Redis — sessions / auth generation / caches
  • Dart WS — match rooms; shared logic mirrored with Flutter
  • Deploy — Docker Compose on VPS rop01 via Ansible playbooks
Not this project: FastAPI + PostgreSQL + Flutter Riverpod template. That is a separate codebase. Dutch’s case study stays faithful to Flask / Mongo / Dart WS.

05 — Pillar 3 · Ops desk

Same repo, browser twin of wfrun

The CLI runner stays default. The dashboard is the place I open when I want scripts, a planning board, marketing compose, revenue KPIs, and docs without leaving Dutch.

  • Scripts — discover and run automation with a live PTY terminal
  • Task Manager — planning board proxied same-origin
  • Marketing — compose once; publish to Facebook, YouTube, TikTok; metrics
  • Revenue — AdMob / Play / App Store estimated + settled; expense ledger; profit
  • Docs / Case Study — browse Documentation/ and this narrative

06 — Impact

What this unlocked

  • A live multiplayer card game on both mobile stores from one solo-owned repo.
  • Honest architecture docs — Flask/Mongo/Dart, not a pretend FastAPI rewrite.
  • Ops, marketing, and revenue live beside the same env the game deploys with.
  • Shared match logic between client and game server reduces “works in practice, breaks online.”
  • Patterns (dashboard, marketing, revenue) can still port to other RoP products without claiming Dutch is the new template.

Scope

Solo end-to-end: game rules and UX, Flask modules, Dart WS, Flutter client, billing, ads, VPS deploy playbooks, and the local ops desk.

What’s next

Keep improving CPU AI and progression catalogs, harden Play GCS revenue access, and deepen marketing metrics — without forcing a premature stack migration.

02 — Principles

Non-negotiables on this older base

  • Features live in modules wired through module_registry / AppManager — not one-off Flask blueprints scattered forever.
  • Match rules shared in backend_core/shared_logic/ between Flutter and Dart.
  • Mongo is the durable store; Redis for session / auth-generation / caches — not Postgres for Dutch gameplay data.
  • Env files SSOT; never log tokens, .p8, or Play service-account JSON.
  • CLI wfrun remains default; dashboard is opt-in.
  • Do not describe Dutch as FastAPI + Postgres — that is a different template.

08 — Hard problems

What production taught

Game / stack

  • Keep Flutter and Dart match logic shared — drift creates “practice works, live doesn’t.”
  • Coin deduct timing on match start vs practice / promotional tier exceptions.
  • Guest + Google + JWT refresh with Redis auth-generation bumps.
  • Store billing: Apple Server API vs Play Billing; AdMob separate from IAP.

Ops / growth

  • Play GCS 403 until SA invited with financial + bulk report account permissions.
  • “All-time revenue” is tracked ledger coverage after Refresh — not a magic lifetime API.
  • ASC sales reports are per-day downloads — slow ranges need patience.
  • Task Manager CSRF fixed with same-origin /tm proxy.
